# 项目结论（2026-10-30）

## 0. 结论来源与验证强度

| 结论 | 来源 | 验证强度 |
|---|---|---|
| E16 最终采用四对 | 设计决策 | 不是 STA，是范围决定 |
| E8 K07 功能通过 | 整核 DiffTest（RTL 仿真） | 仿真验证，不是 STA |
| 面积 1,193.81 µm² / 41 FFs | Yosys + OpenROAD 综合 | 综合结果，不是 STA |
| TT 2.61 ns / 约 383 MHz | OpenROAD STA（`repair_design` + `estimate_parasitics -placement`） | **STA，但为 pre-layout** |
| SS 4.00 ns / 约 250 MHz | OpenROAD STA（SS liberty） | **STA，但为 pre-layout** |
| E8 `BWFastTop` 1.61 ns / 2.73 ns | OpenROAD STA（同一流程，`TOP=BWFastTop`） | **STA，但为 pre-layout** |
| 3 GHz 不达标 | 上述 STA 的 WNS | **STA 结论，非签核** |
| 需要 2–4 级流水化 | 关键路径分析 | 工程判断，不是 STA 证明 |

**pre-layout STA 的含义**：有布局和基于布局的寄生估计，但**没有布线、没有 CTS、时钟理想、没有 OCV/AOCV**。所以 Fmax 是可信的单元级估计，不是签核值；签核还需要 CTS + 布线 + SPEF + SS/OCV 下的 STA。

## 1. 范围结论

**E16 最终采用四对，不采用八对。**

- 最终 E16 数据通路以 `K07E16x4Top` 为基础，不再把“E16 八对”作为目标。
- 当前整核已验证的是 **E8 K07 + 原生八对 E16 回退**；`K07E16x4Top` 尚未接入 `VDotFu`。
- 因此，现有 13 项 DiffTest 通过不能当作四对 E16 的验证结果；四对接入后必须重跑。
- 如果赛题要求 E16 必须是八对，四对实现需要在材料中明确为自定义语义，否则会被判为不完整。

本轮修掉的两个真实问题：

1. **K07 结果的 S2 对齐**：K07 的 E8 结果晚一拍，tail 的 `old_vd/ta/vl` 仍停在 S1，背靠背时高 96 位取了下一条指令的旧值。已在 `VDotFu` 中把 tail 控制和 `VDotCore` 结果全部延迟到 S2。
2. **NEMU 的 tail 语义**：参考模型把高 96 位清零，DUT 按 `vta=0` 保留旧值。已改为 `ta=0` 保留、`ta=1` 全 1。

## 3. PPA 结论（ASAP7 7.5T RVT，pre-layout）

目标单元：`K07E16x4Top`（E16 四对）。

| 指标 | 数值 |
|---|---:|
| 面积（综合后、未缓冲） | **1,193.81 µm²** |
| 寄存器 | **41 FFs** |
| 面积（`repair_design` 后，TT） | 约 **1,206 µm²**（+1.0%，146 buffers） |
| TT 关键路径 | **2,614.5 ps（2.61 ns）** |
| TT 推算 Fmax | **约 382.6 MHz** |
| TT @1 GHz WNS | **-1,636.4 ps** |
| TT @3 GHz WNS | **-2,303.4 ps** |
| SS 关键路径 | **4,004.5 ps（4.00 ns）** |
| SS 推算 Fmax | **约 249.7 MHz** |
| SS @1 GHz WNS | **-3,043.1 ps** |

**结论：3 GHz 远不达标。** TT 约 383 MHz、SS 约 250 MHz，距离 333 ps 还差 8–12 倍。

### 3.1 为什么路径是 2.61 ns / 4.00 ns

| 角 | 总延迟 | 级数 | 缓冲级 | 缓冲延迟 | 逻辑级 | 逻辑延迟 |
|---|---:|---:|---:|---:|---:|---:|
| TT | 2614.5 ps | 48 | 12 | **1459.1 ps（56%）** | 36 | 1155.5 ps（44%） |
| SS | 4004.5 ps | 55 | 10 | **2175.5 ps（54%）** | 45 | 1829.0 ps（46%） |

- **主因是 `sew` 高扇出控制网的缓冲链**：`repair_design` 在 43 个网上插了 146 个缓冲，关键路径上的 `HB3xp67` 单级就要 130–336 ps。`sew` 要驱动整棵压缩树里的模式选择 mux，扇出极大；缓冲又是在布局前插入、之后才 legalize，负载分散导致每级线延迟很长。
- **逻辑深度也不小**：路径还有 36–45 级逻辑，来自 16 操作数压缩树 + 乘法/合并 + 最终 CPA，全部压在一拍内。
- **SS 是 TT 的 1.53 倍**：0.63 V / 100 °C 下库延迟整体变慢，比例与 ASAP7 SS/TT 的典型缩放一致；缓冲和逻辑的占比基本不变。
- **路径起点是 `io_in_bits_sew[1]`（primary input）**：单元级 STA 把输入引脚和边到第一级缓冲的线也算进去了；整核里 `sew` 由寄存器驱动，绝对数会变，但缓冲链和逻辑深度这两个根因不变。

### 3.2 扇出问题与解决方案

**实测扇出**（link 后、`repair_design` 前）：

| 网 | 负载数 |
|---|---:|
| `io_in_bits_sew[0]` | **221** |
| `io_in_bits_sew[1]` | **181** |
| `clock` | 41 |
| `io_in_valid` | 2 |

`repair_design` 报告 **38 个 fanout 违规、33 个 slew 违规、26 个电容违规**，在 43 个网上插了 146 个缓冲。关键路径上的 12 个缓冲级就是这样来的。

问题本质：

1. **`sew` 是全局模式选择信号**，直接驱动压缩树里大量 mux 的 select，单根网扇出接近 200。
2. **缓冲在布局前插入**，不是 placement-aware 的平衡树；负载分散、线长，`HB3xp67` 单级 130–336 ps。
3. **高驱动缓冲换扇出，但带来 slew/电容问题**：33 个 slew、26 个电容违规说明只靠加缓冲是在“拆东墙补西墙”。

可能的解决方案（按优先级）：

| 方案 | 做法 | 代价 | 预期收益 |
|---|---|---|---|
| **A. 局部解码 + 寄存 `sew`** | 在边界把 `sew` 解码成局部 one-hot 选择，寄存后就近分发 | RTL 改动、1 级延迟 | 扇出从 ~200 降到 10–20，缓冲链大幅缩短 |
| **B. 复制 `sew` 驱动** | 把驱动 `sew` 的寄存器复制成 N 份，每份服务一个区域 | RTL 小改、面积略增 | 单网扇出降到 ~20–30 |
| **C. 布局后做 placement-aware buffer tree** | `repair_design` 放到 global placement 之后，fanout 限 8–10，用 `BUFx8/16` 平衡树 | 只改流程 | 每级线延迟下降，预计省 0.3–0.8 ns |
| **D. 重构 mux 结构** | 把 `sew` 选择移到叶子节点，或先算各模式再末尾选择 | RTL 中等改动 | 减少 `sew` 驱动的 mux 数量 |
| **E. 流水化模式选择/压缩树** | 把 `sew` 寄存、压缩树/CPA 切 2–4 级 | 延迟 +1~3 拍、接口改动 | 3 GHz 的必要条件 |

推荐顺序：**先做 C（流程，快，量化扇出收益）→ A+B（RTL，降扇出）→ E（流水化，冲 3 GHz）**。只做 C 最多改善缓冲那 1.5–2.2 ns 的一部分；要真正到 333 ps，A/B/D/E 至少要做两项。

### 3.3 E8 与 E16 四对的时序对比

同一套 OpenROAD 流程（`repair_design` + `estimate_parasitics -placement`）。E8 用 `BWFastTop_asap7_tt_full.v`、`TOP=BWFastTop`：

| 单元 | TT 路径 | TT Fmax | SS 路径 | SS Fmax | 面积 | 缓冲（TT/SS） |
|---|---:|---:|---:|---:|---:|---:|
| E8 `BWFastTop` | **1610.5 ps** | **620.9 MHz** | **2732.9 ps** | **365.9 MHz** | 729.95 µm² / 259 FFs | 62 / 69 |
| E16 `K07E16x4Top` | 2614.5 ps | 382.6 MHz | 4004.5 ps | 249.7 MHz | 1,193.81 µm² / 41 FFs | 146 / 135 |

- E8 比 E16 四对快约 **1.6×**（TT），主要因为 E16 多了合并/乘法通路。
- 两者都远低于 3 GHz；E8 也只有约 **621 MHz（TT）/ 366 MHz（SS）**。
- E8 的 STA 日志：`logs/or_flow_bwfast_1000.log`、`logs/or_flow_bwfast_ss_1000.log`。

## 4. 瓶颈与下一步

瓶颈不是面积，而是**单周期组合路径太深**：

- 16 操作数压缩树；
- 乘法/合并；
- 高扇出 `sew` 模式选择；
- 以上都在一拍内完成。

要接近 3 GHz，需要 **2–4 级流水化**：

1. 把压缩树、最终 CPA、模式选择切开；
2. 重新做 `VDotFu`/`VIAlu` 接口和时序约束；
3. 重新跑整核 DiffTest；
4. 再跑 TT/SS 的 OpenROAD `repair_design` + STA。

如果暂不流水化，当前结果只能作为“未流水化基线”，用于说明优化空间。

## 5. 限制

- **pre-layout**：有布局和寄生估计，无布线、无 CTS，时钟理想；不是整核签核。
- **单元级**：不是整核 PPA；整核还需要 SRAM macro、完整流程和更大资源。
- `vxsat` CSR 写回仍未接通；`vstart>0` 的 K07 语义未完整建模。
- 四对 E16 尚未接入，E16 语义/参考模型/测试/文档都还没按四对更新。
